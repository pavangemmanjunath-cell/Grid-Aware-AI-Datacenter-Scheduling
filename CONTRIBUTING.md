# Contributing

## Welcome

Thank you for considering a contribution. This is research software attached to a peer-reviewed paper, so
the most valuable contributions are the ones that make the results **easier to check, extend or
challenge**: bug reports, independent reproductions, baselines, real-data adapters, documentation and
tests. Please read the [Code of Conduct](CODE_OF_CONDUCT.md) first.

## Ways to contribute

- **Bug fixes** — in the web engine, API, front end, scripts or tests.
- **Features** — new endpoints, visualisations, export formats.
- **Research extensions** — classical baselines, sensitivity or forecast-error studies, factorial
  attribution, sub-hourly resolution, noisy QAOA (see [ROADMAP.md](ROADMAP.md)).
- **Benchmark additions** — new benchmark weeks or sites with documented provenance.
- **Dataset adapters** — mappings from public traces (e.g. Alibaba GPU traces, Renewables.ninja, NESO) to
  the benchmark schema, as download-and-convert scripts.
- **Documentation** — corrections, tutorials, translations.
- **Tests** — especially for `matlab/qh2dc_ingest_trace.m` and edge cases of the API.
- **Reproducibility verification** — run the reproduction on another OS, solver or MATLAB release and
  report the result in an issue.

## Development setup

```bash
git clone https://github.com/<your-user>/Grid-Aware-AI-Datacenter-Scheduling.git
cd Grid-Aware-AI-Datacenter-Scheduling
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt -r webapp/backend/requirements.txt
cd webapp/frontend && npm ci && cd ../..
```

Run everything that CI runs:

```bash
python -m pytest
(cd webapp/backend && python -m pytest)
(cd webapp/frontend && npm run build)
```

## Forking

1. Click **Fork** on GitHub.
2. Clone your fork and add the upstream remote:
   `git remote add upstream https://github.com/pavangemmanjunath-cell/Grid-Aware-AI-Datacenter-Scheduling.git`
3. Keep your `main` in sync: `git fetch upstream && git rebase upstream/main`.

## Branch naming

`feature/<description>`, `fix/<description>`, `docs/<description>`, `research/<description>`,
`benchmark/<description>` — lowercase, hyphen-separated (e.g. `research/greedy-carbon-baseline`).

## Making changes

- **Do not modify the reference implementation** (`matlab/`, `verify/`) or the published artefacts in
  `data/` in a feature PR. If you believe they contain an error, open an issue first; a correction is
  released as a new version with regenerated results (see [ADR-0001](docs/adr/0001-reference-code-immutable.md)).
- Python: type hints, docstrings on public functions, `ruff` style (line length 140, config in
  `webapp/backend/pyproject.toml`).
- TypeScript/React: strict mode, function components, no new runtime dependency without justification.
- Charts: one y-axis per chart, colours by entity from the palette tokens in `styles.css`.
- Keep numbers traceable: anything shown to users must come from `data/`, the engine, or be labelled
  exploratory.

## Testing

Every PR must keep all tests green and add tests for new behaviour. Model changes need a parity or
regression test against a stated reference. Do not weaken a tolerance to make a test pass without
explaining why in the PR.

## Documentation

New capabilities need documentation in the same PR: README or `docs/` page, API docstrings (they become
OpenAPI), and a `CHANGELOG.md` entry under *Unreleased*.

## Research contributions

Describe in the PR or a linked issue:

- the research problem and why it matters for this model;
- the proposed method and its assumptions;
- the evaluation methodology (data, metrics, baselines, seeds);
- supporting references with DOIs where relevant;
- how the result can be reproduced from the repository.

Results must be generated by code in the PR. Do not add numbers that cannot be regenerated.

## Pull request process

1. Fork → 2. branch → 3. modify → 4. test locally → 5. document → 6. open a PR using the template.
A maintainer reviews for correctness, reproducibility and scope. Please keep PRs focused; large changes
are easier to review when discussed in an issue first.

## Data contributions

**Not accepted:** proprietary datasets; private customer data; confidential company data; personal data
without authorisation; copyrighted datasets without redistribution rights; anything containing
credentials or API tokens. Prefer a download script plus a licence note over committing third-party data.
State the licence and source URL of any data you add.

## Contributor attribution

Merged contributions are credited in the release notes and listed in [AUTHORS.md](AUTHORS.md) under
*Contributors* with the contribution category (software, methodology, validation, documentation, testing,
data, visualisation). Contributing code does **not** automatically confer authorship of papers or of the
software citation; that is decided case by case according to the substance of the contribution.
